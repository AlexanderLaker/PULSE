## Part 1 — Explanations

**A4. Covariance, in detail.** Covariance is a number that says: "when thing A moves, does thing B tend to move with it?" Positive = they rise and fall together. Negative = they move opposite. Zero = unrelated. A *covariance matrix* is the full table of these numbers for all pairs of things at once — in our case, the 13 categories. The optimizer uses it to answer "if I put more money in Color and Care, am I really diversified, or am I doubling down on the same risk?" Today the code hard-codes ρ=0.3 for categories in the same business unit (e.g., Hair:Color and Hair:Care) and ρ=0.1 across business units. That's a guess. We have the Monte-Carlo samples — every iteration produces a shift for every category, so if I just run `np.cov()` on those samples I get the *real* covariance the simulation implies, not a guess. Fix is two lines. Then the optimizer's risk estimate actually matches the model.

**A5. Multi-chain Gelman-Rubin, like you're 10.** Imagine three kids are asked "what's the average height of a tree in the park?" Each walks around alone, measures trees, and gives an answer. If all three kids end up with very similar numbers → the measuring is reliable, we trust the answer. If one says 5m, one says 12m, one says 3m → something is wrong, they didn't measure enough. R̂ (R-hat) is just the math version of "how different are the kids' answers from each other versus how much each kid's own answers wobbled?" If R̂ is close to 1.0, the kids agree — we're done. If R̂ is above ~1.05, we need more measurements. Today our code uses *one* kid, cuts their notebook in half, and compares the two halves. That's not the same — one kid can be consistently wrong the same way twice. We need three actual kids (= three independent simulation runs with different random seeds). Small fix.

**A6. Is `causal_decomposition` in the live version?** Yes — `pulse/simulation/bayesian_mc.py` lines 392–414 populates a `causal_decomposition` field in the output that the dashboard consumes. Since we're killing the DAG entirely, I will delete this field. The force attribution (which is what it actually computes) stays, but it gets renamed to `force_attribution` so nothing is labelled "causal" that isn't.

**B1. scipy, simply.** scipy is a well-known, heavily tested Python library for math — things like "solve this optimization," "give me a value from a probability distribution," "do a matrix decomposition." Millions of people use it; bugs get found and fixed publicly. Our code, instead of using scipy directly, goes through a little 188-line file called `_scipy_compat.py` that re-implements some of those functions ourselves. This is risky for two reasons: (1) any math bug in our 188 lines is ours alone to find; (2) if a hacker ever slipped code into that file, we'd never notice. Best practice: just use scipy directly, delete our copy. Zero downside.

**B4. Immutable ModelConfig.** "Immutable" means: once created, nobody can change it. Today the backtesting engine writes directly into `self.config.attenuation` while it's searching for the best value — so if *another* request comes in at the same time using the same config object, the second request sees whatever number the search happened to be trying at that moment. Garbage in, garbage out. Fix: make the config object read-only; any function that wants to change a parameter has to make a copy first. Prevents a whole class of silent corruption bugs.

**B6. RNG seed, explained.** RNG = random number generator. A "seed" is the starting point that tells the generator which sequence of "random" numbers to produce. Same seed → same "random" numbers → same result. Today the code is hard-coded to seed=42 *every single run*. That means (a) every run produces the identical simulation, which hides how much variation there really is, and (b) we can't tell how much of a result is "real" versus "this particular seed got lucky." Fix: let the user pass the seed in, log which seed was used, and run 3 different seeds for any result shown to leadership so we can see the wobble.

**C1. End-to-end golden-file test, explained.** A "golden file" is a frozen, known-good output that we save once. Then every time we change the code, a test re-runs the whole pipeline and compares the new output to the golden file *cell by cell*. If anything differs, the test screams. Without this, a tiny change in, say, the copula code could silently change every Shift Matrix number by 0.5% and no one would notice until the CFO asked "why did Hair:Color move?" With this, we catch it in 5 seconds on the next commit.

**C3. Property-based tests, explained.** Normal tests check one example: "if I put in A, I should get B." Property tests check *a rule that must always hold* across thousands of random inputs. Example rule: "if I increase the attenuation, the absolute shift must not decrease." The test generates hundreds of random model states and checks the rule in every single one. If the rule ever breaks, it tells you exactly which input broke it. Catches bugs that example-based tests never would.

**D5. Velocity on paths vs percentiles, like you're 10.** Imagine 1,000 simulations of how fast a snail moves, year by year. Each simulation is one snail's path. "Velocity" = how much the snail moved this year compared to last year. The right way: measure each snail's year-over-year change, then look at the distribution of those 1,000 velocities — "the slowest 10% of snails sped up by X, the median sped up by Y." The wrong way (what we do now): first compute the median position every year (ignoring individual snails), then subtract. That tells you "how the middle snail moved on average" but not "how fast individual snails are actually changing." For early-warning triggers — which fire on *unusual* speed-ups — you need the first method. Otherwise the trigger thinks everything's calm when in fact 10% of snails are sprinting.

**D6. Accessibility and localization.** Accessibility (WCAG 2.2 AA) = the dashboard works for people with visual or motor impairments — screen readers, keyboard-only navigation, colour-blind-safe palette, large enough touch targets. Localization = German/English language toggle. At a German company presenting to a German Supervisory Board, a tool that only speaks English is unprofessional. Both are "table-stakes" before any Henkel-wide rollout, but neither affects model correctness, so deferring them past the sprint is fine.

**E4. Stale-trend retirement workflow.** The 55 trends don't live forever — some become reality ("Private Label at 42%" — already happened) or become irrelevant. We need a quarterly ritual where someone looks at every trend and asks "is this still a trend, or is it now fact?" and retires the dead ones. Not urgent. Skipping.

**E5. Named red-team / challenger role.** When a model recommends where to put money, you need *someone whose job is to attack the model*. Goldman, McKinsey, every serious quant shop does this. Their job is: "prove PRISM is wrong." Usually one person in the CFO office or Data team. Not a code change — a governance change. You said "no," so skipping.

**F3. ±30% sensitivity band on headlines.** Because the attenuation factor (0.5) is a guess, every headline % in PRISM is secretly "this number ± 30%". Instead of showing "−3.1%", we'd show "−3.1% (range −2.2% to −4.0% just from the attenuation uncertainty)". Makes the honesty visible. One-day fix, high trust value.
